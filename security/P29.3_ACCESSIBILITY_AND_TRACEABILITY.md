### Manual VoiceOver, TalkBack, NVDA passes

**Not performed.** These require a real macOS device with VoiceOver, a real
Android device with TalkBack, and a real Windows machine with NVDA — none
exist in this sandbox. Same category of gap as P29.1's load tests and
P29.2's ZAP baseline: not fabricated. Automated axe coverage (above) catches
a real and large subset of what a manual pass would (missing labels, wrong
roles, contrast, focus order issues axe can detect), but axe is explicitly
not a substitute for a manual screen-reader pass — several classes of real
issue (reading order that's technically valid DOM order but confusing when
heard, gesture conflicts, verbosity) are only caught by ear.

### 200% zoom and 320px width usability

**Not tested before this change** (confirmed by grep — zero existing tests
touched `320`, `zoom`, or set a narrow `viewport`). Added
`tests/e2e/zoom-reflow.spec.ts`, checking `/login`, `/home`, `/discover`, and
`/chats` for `document.documentElement.scrollWidth` overflow at:

- a literal 320px viewport (WCAG 1.4.10 Reflow), and
- a simulated 200% zoom (WCAG 1.4.4 Resize Text — approximated via a halved
  viewport width, the standard technique for this check without a real
  browser-zoom control, which Playwright/Chromium doesn't expose directly).

**Found and fixed a real bug**: `/chats` overflowed horizontally by 51px at
320px width. Root cause: `app/(app)/layout.tsx`'s shared shell (`<main
className="... flex-1">`, nested inside a `flex flex-1 flex-col` wrapper)
had no `min-w-0` on either flex-chain link — a flex item's default
`min-width` is `auto` (its content's own min-content size), so any route
whose content contained an unbreakably-wide descendant would silently force
the _entire shared shell_, and therefore every route nested under it, wider
than the viewport. `/chats`'s filter-chip row was the specific trigger.
Fixed at the shared-layout level (`min-w-0` added to both the wrapper `div`
and `main`) rather than per-route, so the same class of bug can't recur on a
different screen later. Also added `overflow-x-auto` to the chat filter
tablist itself as defense in depth (a horizontally-scrollable chip row is
this app's existing convention for this exact situation — see
`available-now-carousel`, `settings-screen`, `premium-screen`).

All 8 `zoom-reflow.spec.ts` cases now pass.

## Part 2 — Requirement traceability (§22.12)

Full FR-_/NFR-_ evidence walk (148 FR-_, 63 NFR-_) delegated to a research
pass cross-referencing every requirement ID against real test files,
CI config, and enforcement code — not PRD prose. Full per-requirement table
available in the session transcript; summarized here.

### Rollup

_*FR-* (148 total):_* 79 COVERED · 47 PARTIAL · 22 MISSING
_*NFR-* (63 total):_* 14 ENFORCED · 33 PARTIAL · 16 MISSING

"PARTIAL" means: real, passing test evidence exists for the general area, but
the specific requirement's exact boundary/edge case (a char-limit, a specific
enum branch, an exact threshold value) wasn't directly confirmed asserted in
the reviewed test. "MISSING" means no implementation or test evidence was
found at all.

### Systemic gaps this walk surfaced (not previously catalogued together)

1. **No i18n infrastructure at all** (NFR-U-003/004) — zero i18n library
   presence anywhere in `apps/web`, despite en-IN/en-US being a named launch
   requirement.
2. **No infra-as-code in this repo** — most of §9.2/9.3's infrastructure-level
   NFRs (autoscaling, read replicas, PITR backups, zero-downtime deploys) can
   only be verified against a separate infrastructure repo/environment this
   sandbox doesn't have, not against this codebase.
3. **FR-SAFE-010 (GDPR data export), FR-AUTH-012 (2FA/TOTP), FR-AUTH-013
   (Apple Sign-In) are wholly unimplemented**, despite being marked
   P0/MVP-blocker in the PRD. TOTP's absence was already confirmed
   independently during P29.2's security review (T1) — consistent finding
   from two different angles.
4. **Image moderation is a stub for its NSFW/violence half** (FR-SAFE-012 /
   NFR-SEC-009) — AV scanning is real and tested; every file that passes it
   is unconditionally marked `moderationState: "clean"` with no actual
   content classifier wired in. Same conclusion P29.2 reached independently
   for the AV-scanner/classifier stubs.
5. Several PROF sub-features (education, certifications, portfolio, social
   links, profile-view-tracking, change-history) have no discoverable test
   coverage — worth a follow-up pass to confirm whether they're genuinely
   unbuilt or just tested under names/paths this walk didn't surface.
6. `packages/matching` is the one area with a CI-enforced 100% coverage gate
   (`vitest.config.ts`), directly matching NFR-M-001's explicit "100% on
   matching engine" carve-out. `apps/api` has no coverage threshold
   configured at all — worth using `packages/matching`'s config as the
   template for closing that gap.

## Acceptance

P29.3's stated acceptance is "zero critical a11y violations; traceability
report green — a requirement without a passing test blocks the release."

**Automated a11y**: zero violations across all 11 journeys' axe suites,
confirmed by running them. **Manual a11y** (VoiceOver/TalkBack/NVDA): not
performed — no real devices available, stated plainly rather than assumed
clean. **Traceability**: not green — 22 FR-* and 16 NFR-* are genuinely
MISSING, and 47 FR-_/33 NFR-_ are only PARTIALLY evidenced. Per §22.12's own
rule ("a requirement without at least one passing test case blocks the
release"), this is a real, current release blocker, not a formality — stated
as such rather than papered over. The rollup and gap list above are the
concrete, prioritized punch list for closing it.
